# WatchMemo v0.1.0 · 阶段 A 技术验证计划

> 目标：用真机回答三个问题，然后决定能不能进入阶段 B。
>
> 1. **能录多久？** 放下手腕、锁屏、切到其他 App 后，手表录音能否持续？哪种保活方案最可靠、最省电？
> 2. **文件会不会坏？** 录音中 App 被杀、手表重启、存储不足时，最多损失多少音频？
> 3. **同步会不会丢？** 断连、重试、重复传输、App 被杀后，是否存在静默丢失或重复记录？
>
> 配套代码：仓库根目录下的 Demo 工程（`WatchMemoWatch/` + `WatchMemo/`）。所有结论只以真机结果为准。

**通用步骤**

- 每组测试前：手表「设置与日志 → 清空日志」，记录起始电量。
- 每组测试后：手表「发送日志到 iPhone」，在 iPhone「手表日志」中导出并归档到 `docs/test-logs/`。
- 判断后台行为主要看两类日志：
  - `定时器停顿 Ns（App 可能曾被挂起）`：说明这段时间 App 被挂起过。
  - 分段 `完成：xx.xs`：分段的实际时长。分段之间的时间差就是录音缺口。
- 每段录音都要**回放检查**：在 iPhone 上用「顺序播放全部」播放，重点听分段衔接处。

**被测保活方案**（手表「设置 → 保活方案」）

| 代号 | 方案 | 说明 |
|---|---|---|
| M1 | 仅后台音频 | `UIBackgroundModes = audio`，最“正规” |
| M2 | 延长运行会话 | `WKExtendedRuntimeSession`（physical-therapy），有时长上限 |
| M3 | 体能训练会话 | `HKWorkoutSession`，通常最稳；自用可行，上架有审核风险 |

## A3 · 文件完整性

| # | 用例 | 步骤 | 期望 | 结果 |
|---|---|---|---|---|
| A3-1 | 录音中强制退出 | 录 3 分钟（分段 1 分钟）→ 按住侧边按钮，再按住数码表冠强制退出 → 重新打开 | 日志出现“恢复孤儿分段”；已完成的分段全部同步；被杀时那一段**是否能播放**要记录下来 | |
| A3-2 | 录音中手表重启 | 同上，改为重启手表 | 同上 | |
| A3-3 | 录音中没电 | 低电量时长时间录音直到关机（可选）| 关机前完成的分段不丢 | |
| A3-4 | 分段长度对比 | 分段 30s / 1min / 5min 各录 10 分钟 | 记录每种的文件大小、切换缺口、耗电差异，选定默认值 | |

> A3-1 的关键问题：**AAC/m4a 在未正常 stop 时通常无法播放**（文件尾部缺少索引）。如果确认如此，最坏损失就是一个分段长度。届时决定：缩短分段长度，还是改用 CAF/PCM 这类可边写边读的格式（体积更大）。

| # | 用例 | 步骤 | 期望 | 结果 |
|---|---|---|---|---|
| A4-1 | 正常同步 | iPhone 在身边，录 5 分钟 | 分段在结束后数秒～数分钟内到达；手表“待同步”归零 | |

## A6（可选）· 转录预研

阶段 C 才正式做转录，但这一项风险较大，可以提前摸底：

- 用 A1-6 录下的音频，分别测试 iOS 系统语音识别（强制设备端识别）和 WhisperKit。
- 准备 3 段固定样本（纯普通话、中英混合、嘈杂环境），人工校对后计算字错率（CER）。
- 确认系统识别能否在**完全离线**（飞行模式）下转录中文。

## 阶段 A 通过标准（Go / No-Go）

- [ ] 至少一种保活方案能在**放下手腕（S2）**的情况下连续录满 **60 分钟**，单个缺口 < 1 秒。
- [ ] 该方案每小时耗电在可接受范围内（建议 ≤ 25%，按自己的使用习惯定）。
- [ ] A4 全部用例**最终缺失分段为 0**，且没有重复记录。
- [ ] 明确知道 App 被杀时最坏会损失多少音频，并接受这个结果。
- [ ] 选定：默认保活方案、默认分段长度、音频格式。
